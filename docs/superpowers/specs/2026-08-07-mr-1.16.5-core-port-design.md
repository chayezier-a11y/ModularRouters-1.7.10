# Modular Routers 1.16.5 Core Port Design

## Objective

Port the core gameplay of Modular Routers 7.5.4 from upstream branch
`MC1.16.5-master` at commit `5b35f9d` to Minecraft Forge 1.7.10 while preserving
the upstream rules, defaults, recipes, configuration meaning, and observable
module behavior wherever the 1.7.10 platform permits it.

The first milestone excludes optional JEI, TOP, Guide API, and similar
integrations. Compatibility work needed by core module behavior remains in
scope.

## Source Of Truth

- Behavioral reference: upstream Modular Routers 7.5.4, commit `5b35f9d`.
- Target platform: Minecraft 1.7.10, Forge `10.13.4.1614` and Java 8.
- Existing worlds and item NBT must remain loadable.
- Platform APIs may be replaced, but upstream gameplay rules must not be
  changed merely to simplify the port.
- Every code, resource, or design change must be recorded in `HANDOFF.md` in
  the same work session.

## Chosen Approach

Use a layered parity port. Build a feature matrix against 7.5.4, repair shared
router infrastructure first, then port modules in coherent groups. Compile
after each small batch, build after each subsystem, and launch a client for
integration checkpoints.

This is preferred over translating files in repository order because the
1.16.5 capability, container, networking, and energy APIs differ substantially
from Forge 1.7.10. It is also preferred over filling only visible placeholders,
which would leave simplified but incorrect implementations undetected.

## Architecture

### Router State

`TileEntityItemRouter` is the authoritative owner of the item buffer, module
slots, upgrade slots, RF storage, permissions, redstone state, runtime counters,
and persistent NBT. Missing legacy fields use 7.5.4-equivalent defaults. Invalid
enum ordinals and malformed optional configuration fall back safely rather than
crashing world load.

### Module Configuration And Compilation

Module item stacks hold configuration NBT. Installing a module or changing its
configuration marks the router for recompilation. Compilation produces a
runtime `CompiledModule` snapshot so normal execution does not repeatedly parse
NBT. Runtime-only cursors and counters remain outside persistent item
configuration unless the upstream behavior explicitly persists them.

### Compatibility Adapters

Shared adapters centralize platform differences:

- Item transfer uses `IInventory` and `ISidedInventory`, including sided slot
  validation, stack limits, simulation, and rollback.
- Fluid transfer uses the Forge 1.7.10 `IFluidHandler` API.
- Energy transfer uses the included CoFH RF API with `1 FE = 1 RF`; capacity,
  transfer rates, and costs retain their upstream numeric values.
- World interaction uses the router fake player and Forge events for breaking,
  placing, activation, and player-like operations.

Modules must use these adapters instead of implementing incompatible transfer
rules independently.

### Containers, GUI, And Networking

Server containers own real inventory slots and ghost/filter slots. Client GUI
controls only edit local presentation state and send narrow configuration
messages. The server validates player permission, router coordinates, slot
range, installed item type, and requested value before mutating NBT.

The update path is:

1. A player changes module, filter, upgrade, or router configuration.
2. The server validates and stores the change.
3. The router is marked dirty and, where required, marked for recompilation.
4. The server rebuilds compiled state before the next execution cycle.
5. Only client-visible fields are synchronized for GUI and rendering updates.

## Delivery Order

1. Build a 7.5.4 parity matrix and remove false completion claims from the
   handoff record.
2. Stabilize item, fluid, energy, NBT, upgrade, redstone, and permission
   infrastructure.
3. Complete module/filter containers, GUI controls, and validated networking.
4. Port item transfer modules: Puller, Sender, Distributor, Void, Creative, and
   Player.
5. Port world and entity modules: Dropper, Placer, Breaker, Activator, Flinger,
   Vacuum, Detector, and Extruder variants.
6. Port fluid and energy modules.
7. Align recipes, tooltips, language keys, textures, sounds, and configuration
   defaults.
8. Run the complete regression checklist in a dedicated development world.

## Failure And Safety Rules

- Transfers simulate destination capacity before extracting from the source.
- Partial transfers preserve exact remainder stacks and NBT.
- Failed insertion rolls back to the original source whenever possible; if the
  source disappears during execution, the remainder is preserved safely rather
  than silently deleted.
- Invalid targets, unloaded chunks, unavailable dimensions, stale slots, and
  revoked permissions make that execution fail without forcing chunk loads or
  crashing the server.
- Network messages with invalid coordinates, slot indexes, item types, or
  permissions are ignored and logged at an appropriate level.
- No implementation may intentionally duplicate or void items, fluids, energy,
  or experience except for modules whose defined purpose is deletion.

## Verification

- Run `compileJava` after every small implementation batch.
- Run `test` and `build` after each completed subsystem.
- Add focused automated tests for inventory transactions, filter matching,
  upgrade calculations, module NBT defaults, and NBT round trips where the old
  ForgeGradle test environment supports them.
- Launch `runClient` at integration checkpoints and inspect the latest log for
  registration, resource, network, and runtime errors.
- Use a fixed development world to verify router GUI alignment and each module
  behavior, including full destinations, sided inventories, filters, redstone
  modes, unloaded targets, and save/reload behavior.
- Preserve existing test worlds until NBT compatibility and no-item-loss checks
  pass.

## Completion Criteria

The core milestone is complete when every in-scope 7.5.4 item has an explicit
parity status, all non-creative recipes are usable, all core GUI settings round
trip through the server, all modules perform their upstream role under 1.7.10,
RF and fluid transfers obey configured limits, existing worlds reload without
loss, the full Gradle build passes, and the manual regression checklist has no
unrecorded failures.

Any unavoidable 1.7.10 platform deviation must be documented in `HANDOFF.md`
with its user-visible effect and rationale.
